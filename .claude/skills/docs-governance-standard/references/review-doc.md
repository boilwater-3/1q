# Review doc writing standard — docs/review/*.md

审查文档是非规范性审查记录。参考范本：`docs/review/rule14_issue_list_unification_review_2026-08-07.md`
（规则 14 统一问题列表迁移审查——本 skill 的母本）。

## 文件与 frontmatter

文件名：`docs/review/<topic>_review_<YYYY-MM-DD>.md`（topic kebab-case，如
`rule14_issue_list_unification_review_2026-08-07`）。

```yaml
---
Status: draft
Date: <YYYY-MM-DD>
Review-Baseline: `<branch>` @ `<commit>`（N commits，M 文件，+X/−Y）
Authority: 非规范性审查记录；不得替代 `docs/common/contract.md`、
`docs/common/session_contract.md` 及各模块 `docs/<module>/design.md`。
若本文与库实现冲突，以库为准。
---
```

- `Review-Baseline` 必须给分支、基线 commit、提交数、文件数与增减行统计——
  审查范围可复现。
- `Status: draft` 起步；修复全部落库后可改为 `final`（或保留 draft 直到合入）。

## 发现写作规范

1. **每条发现必须带证据列**：`file:line` 精确引用（可多条、可含测试），无证据不列。
2. **严重度**：高（阻断/唯一例外）/ 中（清理或测试缺口）/ 低 / 建议。
3. **发现描述写"契约条款 vs 实现"的对照**：引用规则编号（如"契约规则 9 三写缺一不可"）
   与跨模块对比（"其他四模块均有…；AR 两条路径只有写一+写二"）。
4. **分类判据**：
   - DES — 设计问题（死枚举、零生产调用 getter、手法分裂、死分支、聚合码不对齐）
   - BND — 边界清理（未使用 include、初值不一致、旧符号残留）
   - Q — 质量与正确性（测试空洞、断言缺口、replay 往返丢失）
   - RED — 多余与重复字段（手写重复实现、可推导缓存字段）
5. **"已核查无问题"段落与发现同等重要**：审查后确认无问题的面（旧符号零残留、
   逐字同构、正交性）要明确写出，防止后续重复审查。
6. **编号跨分类连续**：DES-1、DES-2…BND-1…Q-1…RED-1，修复回写按编号引用。
7. **结论中的"机器验证"**：写明构建命令与测试结果，作为可复现基线。

## 后续状态 block（Stage 7 追加，放 §0 末尾）

- 逐条 `编号 → commit` 映射（可一 commit 修多项，用 `DES-2/BND-2/DES-7(ESR) → 401f254d`
  分组写法）。
- 实施中额外发现单独成段，明确"未在原报告 §2 列表"。
- 暂缓项列编号 + 原因（如"ESR status 缓存 vs EOS 推导统一"确认不纳入）。
- 注明"全量测试通过"。
