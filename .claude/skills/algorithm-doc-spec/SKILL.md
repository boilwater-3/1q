# 1Q 算法文档规范与展示格式指南 (Algorithm Doc Specification)

本 Skill 规定了 1Q 项目中所有模块算法文档 (`docs/<module>/algorithms.md`) 的标准展示格式、撰写准则、六要素结构及自动化审计流程。

## 适用场景
- 创建新模块的 `docs/<module>/algorithms.md`。
- 审阅、重构或补充既有模块的 `docs/<module>/algorithms.md`。
- 检查算法文档的工程合规性、边界说明完备性、反直觉点与测试证据链。
- 对既有文档执行**双向审查验收**（正向验证 + 反向清点，见第 6 节）。

---

## 1. 核心定位与权威原则

在 1Q 仿真系统中，`docs/<module>/algorithms.md` 处于**算法工程契约**的权威地位：
1. **工程权威定位**：本文不是学术教科书抄录，而是回答**“用没用 / 到哪步 / 边界在哪 / 哪些反直觉 / 哪些刻意不实现”**。
2. **拒绝空洞**：必须包含确切的数学公式、离散化步骤、物理坐标系约定、参数默认值、数值保护与边界条件。
3. **反直觉点为核心资产**：记录违背直觉但符合工程/物理实情的关键事实（排障与集成的第一防线）。
4. **测试证据硬性绑定**：每项算法必须提供对应的单元测试、集成测试或批处理验证文件锚点。

---

## 2. 文档宏观骨架规范

每个 `algorithms.md` 必须具备以下 5 个结构块：

```markdown
---
Status: active | draft | deprecated
Last-reviewed: YYYY-MM-DD
Authority: <module> 算法登记与实现边界
Answers: <module> 用了哪些算法、各自实现到什么地步、边界在哪、哪些反直觉、哪些刻意不实现
---

# <Module Name> 算法登记

[模块权威声明段落：明确本文在架构中的权威性、源码入口目录 `src/<module>/`，以及与 boundaries.md / data-flow.md / design.md 的分工边界]

## 算法登记表

| 算法/部件 | 意图 / 核心转换 | 实现状态 | 证据与单测 |
|---|---|---|---|
| ... | ... | session-wired | [evidence: tests/unit/...] |

[实现状态的标准取值说明]

## 核心算法详述
[按六要素标准卡片依次展开详述]

## 辅助/映射类算法（可选）
[针对轻量数据转换或辅助步骤，采用紧凑型展示]

## 非目标（刻意不实现的算法）
[列出明确不做、简化或留给外部/上层的非目标，链接到 boundaries.md 或决策文档]
```

## 3. 算法登记总表规范 (Registry Table)

登记总表使用标准 4 列表头：

| 列名 | 规范要求 |
|---|---|
| **算法/部件** | 算法或管线组件的权威名称（可附类名或英文缩写） |
| **意图 / 核心转换** | 传感器/仿真级写一句话业务意图；数据计算级可写“输入 $\to$ 输出” |
| **实现状态** | 严格采用以下 4 种标准枚举之一（见下表） |
| **证据与单测** | 对应的自动化测试文件，统一使用 `[evidence: tests/...]` 格式 |

### 标准实现状态枚举
- **`session-wired`**：已接入 Session / Pipeline 主链路，覆盖配置、执行周期、重放与主集成。
- **`characterized`**：具备局部测试，且有确定性的质量评估与失效矩阵，但未接入 Session 主链。
- **`experimental`**：可编译，有单元测试覆盖，但尚未完成全场景标定与质量验证。
- **`internal/受控`**：库内私有能力或内部支撑工具，不暴露为公开能力契约。
*(历史文档中出现的 `生产可用` 对应 `session-wired`，`实验接线` 对应 `experimental`，建议逐步归一)*

## 4. 算法展示格式：六要素标准卡片 (Six-Element Card)

复杂核心算法必须完整涵盖以下六要素：

### 要素一：算法意图与调用时机 (Intent & Trigger)
- **业务意图**：解决的具体物理、几何或估计问题。
- **调用时机与宿主**：由哪个类/组件（如 `XxxPipeline`、`XxxController`）在生命周期的哪个阶段（如 `RunCycle`、`Update`、`Prepare`）调用。
- **公共/私有归属**：说明核心算法是否由 `common/` 单源提供（如 `BoresightChain`、`ImmFilter`、`DetectionCellResolver`），或是模块私有逻辑。

### 要素二：数学与物理模型 (Mathematical & Physical Model)
- **输入与坐标系**：输入参数、物理量单位、明确的参考坐标系（ECEF、ECI、ENU、机体系、传感器天线系等）。
- **核心公式**：使用标准 KaTeX 表达（行内 `$ ... $`，独立段落 `$$ ... $$`）。
- **分步执行逻辑**：离散化步骤（1, 2, 3...）。
- **参数与阈值表**（若涉及多个权重、门限或断点）：
  | 参数名 | 物理/算法含义 | 默认值 | 单位 / 范围 | 调优影响 |
  |---|---|---|---|---|

### 要素三：实现边界与工程简化 (Boundaries & Simplifications)
- **时空复杂度**：时间复杂度（如 $O(N \log N)$），空间开销，是否有动态内存分配。
- **物理简化与假设**：明确哪些效应做了近似（如平面切平面近似、单星抽帧对齐、无推力模型按能量峰值判定关机等）。
- **状态维护**：无状态纯函数（可并发可重入）还是有状态机（跨周期滑窗/池化；必须说明重置与失跟回收策略）。

### 要素四：边界保护与降级策略 (Corner Cases & Degradation)
- **退化与异常保护**：输入为 NaN/Inf、除零、几何退化（共线/对跖点/平行线）时的处理行为（安全回退、返回空、抛异常或降级真值）。
- **配置防呆保护**：参数超界时的钳制（clamp）或原子拒绝机制。

### 要素五：反直觉点与工程陷阱 (Counter-Intuitive Behaviors)
> [!IMPORTANT]
> 记录违背直觉但符合工程物理实情的关键事实（列举 1~3 点，每点加粗标题说明）。
> 示例：
> - **0 不是缺失而是最危险点**：距离传 0 表示零距离满分威胁，缺失必须显式传 NaN。
> - **置信度可超过 1.0**：按滑窗内证据精确求和，不是归一化概率。
> - **回推误差随时间发散**：回推协方差包含模型漂移增长项，大于当前状态误差属正常物理规律。

### 要素六：证据链 (Evidence & Verification)
- **源码入口**：`src/<module>/...`
- **测试证据**：`[evidence: tests/unit/<module>/xxx_test.cpp]`

## 5. 辅助与轻量算法展示规范 (Compact Profile)

对于简单的坐标换算、纯枚举查表或轻量数据映射，可采用紧凑格式，但必须保留核心 4 条：
- **- **意图**：...**
- **- **规则 / 步骤**：...**
- **- **实现边界与反直觉点**：...**
- **- **证据**：`[evidence: tests/...]`**

## 6. 审查流程：双向核对（正向验证 + 反向清点）

对既有 `algorithms.md` 的审查（重写验收、阶段评审、定期复审）**必须两个方向都做**，缺一必有漏网：正向验证挡不住"文档根本没提的能力"，反向清点挡不住"写了但写错了"。

### 6.1 正向验证（文档 → 代码）

文档中每一条硬性声明逐条打开代码核对，不允许"看起来合理"放过：

| 声明类型 | 核对要点 |
|---|---|
| 路径/符号 | 文件、类、函数、枚举名在代码中真实存在（警惕编造或改名的入口，如 `RunDwellCycle` vs 实际 `RunCycle`） |
| 数值 | 默认值、常量、钳位范围、阈值与配置头文件逐字一致（含默认是否为零/是否开启） |
| 公式 | **按代码重推系数，警惕照抄教科书形式**——典型翻车：σ = c/(2B·√(2·SNR)) 教科书式 vs 代码工程系数 0.5·δ_R/√SNR；GMST 秒制 Aoki 0h-UT1 常量 vs 代码度制 Vallado 形式（代入满儒略日恒差 180°） |
| 语义方向 | 增益乘分子还是除分母（SINR 账本各项方向不对称）、门守卫哪条状态转移边、偏置施加在均值侧还是方差侧、归约是 argmax 还是求和、平均是等权还是质量加权 |
| 坐标系/归属 | ECEF/ENU/ECI/传感器系不张冠李戴；"common 单源"确实在 `src/common/` 且模块侧确实只是薄封装 |
| 接线 | 实现状态枚举与实际接线一致（`session-wired` = 真在 Session/Pipeline 主链上被调用） |
| 证据 | `[evidence: ...]` 锚点文件在盘且确实覆盖该算法；`文件:行号` 形式引用逐个打开核对（行号漂移也算问题） |
| 版本对照 | `git show HEAD:<path>` 对照上一版——重写/压缩时删失的边界表、反直觉点、证据锚点按规范应保留的必须报告 |

问题分级：**高** = 与代码相悖（错路径/错名/错值/语义方向错/公式错）；**中** = 不准确、过时、歧义、证据缺失、应有内容丢失；**低** = 格式与措辞。

### 6.2 反向清点（代码 → 文档）

正向审查之后必须做反向兜底，否则"文档没写的能力"永远发现不了：

1. **枚举全量源文件**：`find src/<module>/ -name "*.cpp" -o -name "*.h"`，逐个文件对照登记表与详述节，标记零提及部件。
2. **判定遗漏还是豁免**：session 层 replay/validation/adapter、runtime config mapper、纯数据结构头文件属于管线与契约基础设施，归 boundaries.md / data-flow.md 范畴，**不算** algorithms.md 遗漏；含实质算法内容（模型、口径、门控、融合、误差、派生量、可配置能力面）而文档零提及的，是遗漏。
3. **遗漏补登记**：够分量的加登记行（配六要素卡片或并入相邻卡片）；轻量的进「辅助/轻量算法」紧凑卡。补上的证据锚必须实际覆盖——先 grep 测试文件确认再写锚，不为凑数引不相干测试。
4. **多模块分阶段执行**：按模块派发（可用 subagent 并行），每模块两个方向都做；已审模块先行提交，未审模块不入同一提交。

## 7. 工具与脚本 (Tooling)

本 Skill 配备了自动化检查脚本：
`python .agents/skills/algorithm-doc-spec/scripts/lint_algorithms_md.py docs/<module>/algorithms.md`

### 检查项：
1. **Frontmatter**：完整性（`Status`、`Last-reviewed`、`Authority`、`Answers`）。
2. **总表规范**：表头列数（4 列）、实现状态枚举合法性。
3. **算法展示完整性**：核心章节是否具备意图、边界、反直觉点、证据链。
4. **证据文件可达性**：检测 `[evidence: tests/...]` 中的文件是否存在于代码库中。
