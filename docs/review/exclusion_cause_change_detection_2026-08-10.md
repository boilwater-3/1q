# 排除原因跨周期变化检测：需求与设计讨论记录

## 0. 定位与结论

本记录书面化"排除原因跨周期变化检测"需求（规则 13b 排除诊断的差分观测），作为后续实施的
需求规格与设计决策依据。**需求已确认（含进入/退出排除转换），尚未实施**。

核心结论：

1. **cause 字段（规则 13b 门内归因，已落地）是变化的"原料"而非替代品**：变化事件 =
   差分(本周原因, 上周原因)，没有每周期快照就没有差分；不存在"跳过 cause 直接做事件"的更优
   路径。
2. 本需求的前置条件是**排除诊断的实体机器可读关联**（`location.kind=kSceneEntity` +
   `entity_index`）——当前 target_id 仅存在于 message 人读文本，记录器无法判定"该排除属于
   哪个实体"。该关联与 cause 同属原料层，是实施本需求前必须补齐的地基。
3. 实施范围建议：**先 AR 试点，验证事件形态与消费价值后再铺开 SBIRS/EOS/ESR**；SAR 无排除
   诊断（13b 空洞条款），不适用。

## 1. 背景与动机

规则 13b 排除诊断（kInfo）已通过 `cause` 结构化字段给出**每周期**目标/发射源被排除的主因
（如 `ArIssueCause::kRcsLimited`、`SbirsIssueCause::kDistanceLimited`）。该信息是**瞬时快照**：
每个执行周期独立产出，跨周期不携带任何记忆。

当前缺口：目标长时间未被探测时，其排除原因可能随时间变化（如从"RCS 主导"变为"波束偏轴
主导"），这一**变化本身**目前没有任何观测载体——集成方只能逐周期对比自己落盘的数据才能
发现，且各集成方需各自实现差分逻辑。

## 2. 需求规格

### 2.1 目标

在库内提供"排除原因跨周期差分检测"能力：对持续被排除的实体（目标/发射源），当其排除原因
发生变化时产生结构化事件，与既有生命周期事件（如 `kFirstConfirmed`/`kLost`）同流输出，
供集成方在线监控与统一时序分析。

### 2.2 适用范围

适用于所有具有"按实体门控排除"语义的模块（规则 13b 非空洞模块）：

| 模块 | 排除实体 | 原因维度 |
|---|---|---|
| airborne_radar | 目标（target_id） | SNR 聚合门四因（距离/波束/噪声底/RCS） |
| sbirs_sensor | 目标（target_id） | 四门（遮挡/距离/视场/SNR 构成） |
| electro_optical_sensor | 目标（target_id） | 视场门（越界轴） |
| electronic_surveillance_radar | 发射源（platform/equipment/emission id） | 零功率成因/检测门型 |

不适用：sar（无逐目标门控排除，13b 空洞条款，无排除诊断）。

### 2.3 需求场景

场景 A（原始动机）：

> 探测开始后，某几个目标探测不到，排除原因是 a（如 `kRcsLimited`）；运行一段时间后，
> 排除原因变为 b（如 `kBeamLimited`）。

期望：集成方能观测到"目标 X 的排除原因从 a 变为 b"这一转换——包括**何时发生**（周期号）、
**哪个实体**、**新旧原因**，且无需自行逐周期比对落盘数据。

完整转换语义（已确认纳入）：

- **A1 原因稳定**：持续被排除且原因不变（a → a）：**不产生事件**（事件化，不刷屏）。
- **A2 进入排除**：未被排除 → 被排除（kNone → a）：产生进入事件。
- **A3 原因变化**：被排除中原因变化（a → b，a ≠ b）：产生变化事件（**本需求核心**）。
- **A4 退出排除**：被排除 → 不再被排除（a → kNone）：产生退出事件（与"恢复探测"对应）。

### 2.4 行为规格

1. 每个**执行周期**（`status == kCompleted`）对每个被排除实体记录其排除原因（该周期排除
   诊断的 `cause`）。
2. 与上一执行周期同实体的原因比较，按 2.3 转换规则产生事件；原因未变化不产生事件。
3. 事件携带：周期号、实体标识（target_id / 发射源标识）、旧原因、新原因、关键量值
   （人读辅助）。
4. 非执行周期不产生事件、不推进内部状态（与既有 LifecycleRecorder 语义一致）。
5. 纯观测：不改变 `*CycleStatus`、排除诊断、DebugView 状态语义（规则 13c 边界延续）。
6. 事件与既有生命周期事件同流输出（同一 `GetLastEvents()` 通道），集成方按事件种类分流
   消费。

### 2.5 边界与约束

- 原因比较基准为各模块 `<Module>IssueCause` 枚举；`kNone`（未被排除）参与转换判定
  （A2/A4）。
- 内部状态最小化：每实体仅需记忆上一周期原因（单个枚举值），符合 LifecycleRecorder
  "状态最小化"设计原则。
- 记录器注册/注销不影响执行语义（与既有 recorder 契约一致）。

### 2.6 非目标（本需求明确不做）

- 不改变排除诊断的产出与语义（issues 仍是每周期全量快照通道）。
- 不做原因"预测/预警"（仅在变化发生后报告）。
- 不提供跨周期查询 API（调用方按规则 12 落盘事件流获得历史）。

### 2.7 前置依赖

排除诊断须具备**实体机器可读关联**：排除 issue 的定位字段应结构化携带实体索引
（`location.kind = kSceneEntity` + `entity_index`；ESR 以发射源标识为键），否则记录器无法
判定"该排除属于哪个实体"。该关联当前缺失（target_id 仅存在于 message 人读文本），是本需求
实施的前置条件，建议随 cause 同批补齐（各模块排除发射点约各 2 行 + 测试）。

## 3. 设计讨论记录

### 3.1 为什么 cause 快照先行，而不是直接做事件

变化检测在数学上是 `变化事件 = 差分(本周期原因, 上周期原因)`——**没有每周期快照就没有
差分**。任何"直接做事件"的替代方案都必须先定义事件里"原因 a/b"的表示，绕不开三选一：

| 替代路径 | 问题 |
|---|---|
| 事件里用细分 code 当原因 | 回到码膨胀（43 个执行码教训），且 code 是冻结契约 |
| 事件里用内部枚举（不暴露为 Issue 字段） | 每周期快照仍缺失：落盘分析、离线对比、replay 保真、其他消费方全不可用；枚举定义两遍 |
| 不做库内字段，调用方差分 | 每个集成方重复实现，且"当前原因"无机器可读通道 |

结论：cause 字段是变化的**原料**，先行落地正确（已在 `feature/exclusion-diagnosis-cause`
落地：Issue 结构 + 枚举 + replay 保真 + 契约条款）。不存在"更早一步到位"的路径——除非放弃
每周期快照的全部消费场景（落盘、replay、离线分析）。

### 3.2 收益分析（为什么先试点）

cause 字段落地后，本需求的收益是"呈现方式"而非"新信息"：

| 增量 | 价值 | 说明 |
|---|---|---|
| 在线事件化（变化即发，不刷屏） | 中 | 适合告警/实时监控；落盘+离线对比做不到实时 |
| 与生命周期事件同流 | 中高 | "丢失 → 原因变化 → 恢复"统一时序分析 |
| 各集成方免重复实现差分 | 中 | 公共能力进库 |

原因维度最丰富、变化检测价值最大的是 AR（SNR 四因）与 SBIRS（四门多因）；EOS 仅视场外
一维原因（az/el/both），SAR 无排除。故实施建议：**AR 试点 → SBIRS 跟进 → EOS/ESR 按需**。

### 3.3 事件形态（待试点确定）

两种候选，AR 试点时定夺：

- 扩展既有事件种类（如 AR `kNotTracked` 增加原因字段/枚举值）：复用现有通道，但"原因变化"
  与"无 track 事实"语义混叠。
- 新增独立事件种类（如 `kExclusionCauseChanged`，携带 old_cause/new_cause）：语义清晰，
  与既有事件并列。

## 4. 未决问题

1. 事件形态：扩展既有事件 vs 新增事件种类（§3.3，AR 试点定夺）。
2. 进入/退出事件（A2/A4）是否与生命周期事件（`kFirstConfirmed`/`kLost`）存在重复语义——
   需在试点时对齐边界（如"退出排除"与"kLost"的先后关系）。
3. 契约落位：若实施，规则 13b 是否增补"排除原因变化事件"条款，或仅模块 boundaries 登记。
