# 机动模块测试设计分析报告

> 分析对象: `tests/unit/fd_adapter_test.cpp`
> 分析范围: 运输机(9机型)、战斗机(7机型)、通航飞机(5机型) 对6种机动模式的参数化测试
> 分析日期: 2026-05-26

## 一、整体架构

测试文件采用 **1个基础Fixture + 3个参数化测试套件** 的结构：

| 套件 | 机型数 | 测试用例数 | 机动模式覆盖 |
|------|:------:|:---------:|:-----------:|
| FlightDynamicTest (c172x) | 1 | 13 | 6/6 + 辅助功能 |
| FighterDynamicTest | 7 | 6×7=42 | 6/6 |
| TransportDynamicTest | 9 | 6×9=54 | 6/6 |
| GADynamicTest | 5 | 6×5=30 | 6/6 |
| **总计** | **21** | **139** | **完整** |

覆盖了21个机型 × 6种机动模式 = 126种组合，表面上看覆盖面完整。

## 二、测试标准问题 -- "能跑"≠"正确"

**这是最核心的问题。** 参数化测试几乎全部是 **smoke test（冒烟测试）**，只验证了状态机转换，没有验证任何物理行为的正确性。

具体来看每个机动模式的断言：

| 机动模式 | 参数化测试的断言 | 缺失的关键验证 |
|----------|-----------------|---------------|
| **FlyToWaypoint** | `state == kExecuting`（100步后仍在执行） | 飞机是否朝目标转弯？位置是否在移动？航向是否在变化？ |
| **Orbit** | `state == kExecuting` | 飞机是否在绕圈？是否产生了横向位移？ |
| **SetHeading** | `state == kExecuting` | 航向是否向目标值收敛？航向误差是否在减小？ |
| **SetAltitude** | `state == kExecuting` | 高度是否在变化？升降率是否合理？是否朝目标高度移动？ |
| **SetPitch** | `state == kCompleted`（唯一的完成断言） | 实际俯仰角是否接近5°？是否在持续时间内保持？ |
| **SetRoll** | `state == kCompleted`（立即完成） | 滚转模式是否被正确设置？ |

**对比基础Fixture的测试**，它更深入一些——检查了 `sim_time_sec > 0` 和 `mass_kg > 0`，但仍然没有验证物理量的变化方向。

**结论**：如果某个机型的 SetHeading 实际上把飞机带到了相反方向，或者 SetAltitude 让飞机下降而非爬升，这些测试 **全部会通过**。

## 三、可靠性问题

### 3.1 仿真时长不足

所有参数化测试统一运行 **100步 = 0.5秒**。这个时长对于以下场景远远不够：

- **运输机SetAltitude**：737从3000m爬升到3500m（+500m），爬升率约2-3 m/s，实际需要150-250秒。0.5秒内飞机几乎还没开始动。
- **运输机FlyToWaypoint**：目标在`0.01 rad ≈ 637 km`外，130 m/s的运输机需要约80分钟。0.5秒后飞机刚完成初始转弯。
- **战斗机SetHeading**：f15从0°转到90°（1.57 rad），最大滚转角限制在30°，高速转弯需要10-30秒。0.5秒只能完成转弯的初始阶段。

**这意味着**：这些测试实际上只验证了"机动命令被接受且仿真没有崩溃"，而非"机动在合理时间内产生了预期效果"。

### 3.2 缺少中间状态验证

测试只在最终状态（100步后）做断言，没有在仿真过程中采样验证。例如：
- 没有检查仿真过程中飞机是否出现不合理的状态跳变
- 没有检查是否出现了 NaN 或发散
- 没有检查控制面偏转是否在合理范围内

### 3.3 异常处理方式

参数化测试用 `try/catch` 包裹整个测试体，失败时报错 `"Fighter model X FlyToWaypoint failed: ..."`. 这比不处理要好，但 GTest 的 `EXPECT_*` 宏已经内置了失败报告机制，`try/catch` 主要捕获的是未预期的异常（如JSBSim内部错误），对逻辑错误无效。

## 四、逻辑性问题

### 4.1 三套测试几乎完全重复

FighterDynamicTest、TransportDynamicTest、GADynamicTest 的测试体 **代码完全相同**，只有前缀字符串不同（`"Fighter model"` vs `"Transport model"` vs `"GA model"`）。这违反了 DRY 原则，应使用模板基类或参数化测试工厂。

### 4.2 缺少机型差异化测试

所有机型使用 **相同的测试参数**（相同的航向、相同的高度增量、相同的航点半径），没有根据机型特性调整：

- **战斗机** 应该测试更激烈的机动（大坡度转弯、快速爬升），因为其设计包线与运输机截然不同
- **运输机** 应该测试更温和的机动参数，验证大惯性飞机的响应特性
- **通航飞机** 应该测试低速下的机动能力边界

### 4.3 SetAltitude 只测爬升，不测下降

所有 SetAltitude 测试都用 `altitude_m + 500.0`，即只测试爬升。下降机动完全未覆盖，而下降涉及不同的空气动力学特性（如需要减小推力、可能的速度增加等）。

### 4.4 缺少 FlyToWaypoint 的完成验证

基础Fixture的 `FlyToWaypointManeuver` 只验证了 `kExecuting || kCompleted`，这是一个 **模糊断言**——它总是为真。没有验证飞机是否真正到达了目标附近。WaypointManager 的 `IsAtTarget()` 逻辑（距离 < 100m）从未在测试中被触发验证。

### 4.5 Orbit 机动语义不清

代码注释说 Orbit "currently modeled as a single waypoint with a radius, so it will complete when the waypoint manager finishes (not an indefinite loiter)"。这意味着 Orbit 实际上是一个 **有限操作**，会像 FlyToWaypoint 一样完成。但测试没有验证这个行为，也没有测试当 Orbit 完成后的状态。

## 五、鲁棒性问题 -- 完全缺失

以下场景 **没有任何测试覆盖**：

| 鲁棒性场景 | 重要性 | 说明 |
|-----------|:------:|------|
| **边界值** | 高 | 航向 = 0°/360°（穿越正北）、航向 = ±π |
| **极端机动** | 高 | 俯仰角 = ±15°（控制器限幅边界）、高度变化 = ±5000m |
| **并发机动** | 中 | 同时发出矛盾命令（如 SetHeading 和 SetAltitude 同时激活时的优先级） |
| **异常参数** | 中 | 负的orbit半径、超大航向角（> 2π）、NaN输入 |
| **仿真越界** | 高 | 飞机撞地（高度降到0以下）、失速、超速 |
| **长时间运行** | 中 | 运行1000+步，验证数值稳定性、无发散 |
| **Reset后行为** | 中 | 基础Fixture测了Reset，但参数化测试未测 |
| **Abort语义** | 中 | 只在基础Fixture测了Abort，参数化测试未覆盖 |
| **机动队列** | 中 | 多个机动排队执行（如 FlyToWaypoint → SetHeading → SetAltitude）只在基础Fixture中简单测了 |
| **JSBSim-native vs C++ autopilot** | 高 | 部分机型（c172x, c310）内置了JSBSim自动驾驶仪，会走不同的代码路径，但测试没有区分 |

## 六、总结

| 维度 | 评分 | 说明 |
|------|:----:|------|
| **测试标准** | ★★☆☆☆ | 只验证了"不崩溃"，未验证物理正确性 |
| **可靠性** | ★★☆☆☆ | 仿真时长严重不足，无法触发真正的机动效果 |
| **逻辑性** | ★★★☆☆ | 机型覆盖完整，但测试参数一刀切、缺少差异化 |
| **鲁棒性** | ★☆☆☆☆ | 几乎没有边界、异常、长时间运行测试 |

**核心结论**：当前的参数化测试本质上是 **集成冒烟测试**（"这个机型+这个机动命令不会崩溃"），而非 **功能正确性测试**（"这个机动命令产生了预期的物理效果"）。对于一个飞行仿真模块，这意味着即使控制律存在严重错误（如航向控制器增益符号反了），测试也可能全部通过。

**建议优先改进方向**：
1. 为 SetHeading、SetAltitude 增加物理量断言（航向误差减小、高度变化方向正确）
2. 延长关键机动的仿真时长，或改为"运行直到完成或超时"的模式
3. 增加下降机动、边界航向、长时间运行等鲁棒性测试
4. 用模板基类消除三套测试的代码重复
