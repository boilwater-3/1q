# Signal 层架构说明

## 1. 设计目标

Signal 层负责把探测量测逐步加工为可持续维护的稳定航迹，并为后续决策层和目标分类模块提供可靠输入。

当前最重要的架构原则不是“把所有目标处理都塞进一个模块”，而是明确以下边界：

- 数据关联只负责“这次量测属于哪条航迹”。
- 跟踪滤波只负责“这条航迹的状态怎么预测和更新”。
- 轨迹管理只负责“这条航迹是否新建、确认、丢失或回收”。
- 对象池只负责内存复用，不承担航迹业务语义。

## 2. 核心职责拆分

### 2.1 回波计算

职责：

- 基于雷达方程、传播损耗、杂波和干扰环境估计目标回波功率。
- 为探测判决提供物理层输入。

### 2.2 信号检测

职责：

- 计算信噪比、探测裕量或探测概率。
- 对每个候选目标做是否探测成功的判决。
- 输出有效量测或量测质量信息。

### 2.3 数据关联

职责：

- 根据波门、距离度量、代价矩阵等方法，将新量测分配给已有航迹预测。
- 输出关联结果、未关联量测和未命中航迹集合。

不负责：

- 新航迹确认
- 丢失与回收策略
- 轨迹对象生命周期维护

### 2.4 跟踪滤波

职责：

- 基于关联结果进行状态预测、量测更新、平滑和外推。
- 维护位置、速度、加速度、协方差等状态估计量。

不负责：

- 决定航迹是否应该确认或删除
- 管理对象池

### 2.5 轨迹管理

职责：

- 维护航迹生命周期状态机：候选、确认、丢失、回收。
- 维护轨迹编号、批号、命中计数、失配计数等管理信息。
- 统一决定何时申请轨迹对象、何时归还对象池。
- 对外导出稳定的航迹快照或目标特征快照。

这是目标分类模块真正依赖的直接上游，因为分类不应消费单帧临时量测，而应消费经过关联、状态估计和生命周期管理后的稳定目标表示。

### 2.6 对象池

职责：

- 提供轨迹对象的申请与归还。
- 降低频繁创建和销毁轨迹对象的内存开销。

不负责：

- 目标状态机
- 批号推进
- 丢失判定
- 回收策略

## 3. 大白话理解

如果不从算法公式出发，而是从“每个模块到底在干什么”来理解，Signal 层里最容易混淆的三个模块可以用下面三句话记住：

- 数据关联：这次新看到的量测，到底是不是上一拍那个目标。
- 跟踪滤波：这个目标现在到底在哪里、速度多大、运动趋势怎样。
- 轨迹管理：这条航迹现在算不算有效，应该新建、确认、丢失还是回收。

### 3.1 数据关联在干什么

可以把数据关联理解成“认人”。

每个周期雷达都会得到一批新的量测点，但系统里可能已经有一些旧航迹。数据关联要做的，就是判断“这个新点应该接到哪条旧航迹上”。

它回答的问题是：

- 这个量测属于哪条已有航迹。
- 这个量测是否谁都对不上。
- 哪条旧航迹在本周期没有等到新的匹配量测。

它不回答的问题是：

- 这条航迹的速度到底是多少。
- 这条航迹应不应该删除。
- 这条航迹对象是否应该回收到对象池。

### 3.2 跟踪滤波在干什么

可以把跟踪滤波理解成“看人看得更准”。

数据关联只说明“这个点大概率属于这条航迹”，但量测本身通常有误差、有抖动，也可能受环境和干扰影响。跟踪滤波会把历史状态和当前量测结合起来，估计出更稳定的目标状态。

它回答的问题是：

- 目标现在更可能在哪。
- 目标现在的速度、加速度大概是多少。
- 下一拍目标可能会出现在哪里。

它不回答的问题是：

- 这条航迹是不是已经可以确认。
- 这条航迹连续丢了几次后应不应该回收。

### 3.3 轨迹管理在干什么

可以把轨迹管理理解成“管档案”。

它不是在做数学估计，而是在维护航迹的业务生命周期。也就是说，它负责判断一条航迹现在到底处于候选、确认、丢失还是回收状态。

它回答的问题是：

- 一个新量测是否值得新建航迹。
- 一条候选航迹命中足够多次后是否转为确认。
- 一条确认航迹连续失配后是否转为丢失。
- 一条丢失航迹是否已经超时，需要回收并归还对象池。

它也负责维护：

- 轨迹编号
- 批号
- 命中次数
- 失配次数
- 生命周期状态

### 3.4 为什么一定要拆开

因为这三件事本质不同：

- 数据关联管“谁对谁”。
- 跟踪滤波管“它现在怎么动”。
- 轨迹管理管“它还算不算一条有效航迹”。

如果把三者揉成一个模块，后面一改关联算法，建轨规则就容易被带乱；一改滤波器，回收策略也容易跟着被污染。拆开之后，每个模块只对自己的职责负责，后续目标分类也才能拿到稳定、可解释的上游数据。

## 4. 主处理链路

从一次处理周期的角度，Signal 层的合理主链路如下：

1. 环境模型与输入状态共同生成当前周期的回波与探测条件。
2. 信号检测输出有效量测。
3. 数据关联将量测与已有航迹预测进行匹配。
4. 跟踪滤波根据关联结果更新目标状态。
5. 轨迹管理根据命中和失配情况推进生命周期状态机。
6. 轨迹管理导出稳定航迹快照，供决策层与目标分类使用。

## 5. 与目标分类模块的关系

目标分类模块后续需要的输入，不应直接来自单帧检测输出，而应来自轨迹管理导出的稳定目标表示，并在此基础上继续提取分类特征。

建议分类上游分两层：

1. 轨迹管理输出基础状态
- 位置、速度、加速度
- 轨迹状态
- 命中/失配计数
- 批号与轨迹编号
- 历史窗口索引或历史摘要

2. 分类特征提取器输出分类向量
- RCS 统计特征
- 速度与机动统计特征
- 航迹稳定性与观测质量特征
- 场景修正特征

## 6. 当前实现映射

当前代码中与上述边界对应的关键位置如下：

- `SignalPipeline`：承担简化的信号处理周期实现。
- `TrackLifecycleManager`：承担轨迹生命周期推进与快照导出。
- `ITrackPool` / `BoostTrackPool`：承担轨迹对象内存复用。
- `TrackMeasurement`：表示关联后的量测输入。
- `TrackState`：表示对象池中的重对象状态。

说明：

当前代码中，数据关联模块和跟踪滤波模块的完整实现仍在演进中，因此本文档描述的是“推荐且正在收敛的目标架构边界”，不是声称所有模块都已完整落地。

## 7. 当前建议

如果后续要继续推进目标分类模块，Signal 层应优先完成以下事项：

1. 明确数据关联输出契约。
2. 明确跟踪滤波输入输出契约。
3. 保持轨迹管理作为唯一生命周期状态机入口。
4. 在轨迹管理之后再定义分类特征提取器。

只有这样，目标分类模块才能建立在稳定、可解释、可扩展的数据基础上。
